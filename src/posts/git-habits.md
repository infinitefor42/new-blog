很多人用 Git 只会三板斧：

```bash
git add .
git commit -m "修改"
git push
```

这没有错，但项目一大、时间一长，问题就来了：翻提交历史像看天书，根本不知道哪次改了什么；出了 bug，也不知道该从哪个版本开始找。

好习惯越早养成，后面越省事。下面这六个习惯，说到底都是写给未来的自己——现在多花一分钟，是为了将来少返工一次。

---

## 一、提交信息要写清楚

**反面教材：**

```bash
git commit -m "改了东西"
git commit -m "bug fix"
git commit -m "aaa"
```

**正确做法：**

```bash
git commit -m "feat: 新增用户登录功能"
git commit -m "fix: 修复首页在手机端样式错乱的问题"
git commit -m "docs: 更新接口文档"
git commit -m "refactor: 重构数据请求模块"
```

格式是 `类型: 具体说明做了什么`。常用类型如下：

| 类型 | 含义 |
| :--- | :--- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 改文档 |
| `style` | 调整格式（不影响代码逻辑） |
| `refactor` | 重构（既不是新功能也不是修 bug） |
| `perf` | 性能优化 |
| `test` | 增删改测试代码 |
| `chore` | 杂项（构建、依赖、配置等） |

> 写清楚提交信息，三个月后翻历史记录，你会感谢现在的自己。

---

## 二、小步提交，不要攒着提

很多新手喜欢写一天代码，最后一次性全提交。这样做的隐患是：一旦出错，**只能整体回退**，没办法精确撤销某一个改动。

正确做法是做完一个小功能点就提交一次：

```bash
git commit -m "feat: 完成登录页面布局"
git commit -m "feat: 完成登录接口调用"
git commit -m "fix: 修复登录成功后跳转路径错误"
```

每次提交都相当于一个存档点。出问题时，可以精准回到任意一个节点，而不是被迫丢掉一整天的成果。

---

## 三、一定要用 .gitignore

有些文件不应该被 Git 管理：

* `node_modules/`：依赖包，体积巨大，没必要上传
* `.env`：里面有数据库密码、密钥等敏感信息
* `dist/`：打包产物，每次构建都会重新生成
* `*.log`：日志文件，随时在变

在项目根目录创建 `.gitignore` 文件：

```gitignore
# 依赖
node_modules/

# 环境变量与密钥
.env
.env.local

# 构建产物
dist/
build/
out/

# 日志
*.log

# 系统文件
.DS_Store
Thumbs.db
```

写进去的文件 Git 会直接忽略，再也不会误提交。

> ⚠️ **注意**：`.gitignore` 只对**尚未被追踪**的文件生效。如果敏感文件已经被提交过，光加进 `.gitignore` 是没用的，必须先用 `git rm --cached .env` 把它从版本库中移除。

## 四、用分支隔离开发

不要所有代码都堆在一个分支上，至少保持两条常驻分支：

* `main`：稳定版本，随时可以运行
* `develop`：日常开发的地方

开发新功能时，从 `develop` 再开一条特性分支：

```bash
git switch -c feature/购物车功能
```

做完再合并回 `develop`：

```bash
git switch develop
git merge feature/购物车功能
```

这样做的好处是：新功能开发到一半，突然需要临时修一个 bug，直接切分支处理，两边互不影响。

> 顺带一提，切换/创建分支推荐用较新的 `git switch`，比老写法 `git checkout` 语义更清晰、更不容易误操作。

---

## 五、推送前先拉取

团队协作时，推送前一定先拉取别人的最新代码：

```bash
git pull
git push
```

不这样做，很容易出现推送失败，或者和别人的代码产生冲突。养成「推送前先拉取」的习惯，能省去很多不必要的麻烦。

如果想让提交历史保持线性整洁，可以用变基方式拉取：

```bash
git pull --rebase
```

---

## 六、后悔了别慌

常见的误操作，都能救回来：

| 场景 | 命令 |
| :--- | :--- |
| 文件改错了，想撤销工作区的改动 | `git restore .` |
| 已经 `add` 了，想取消暂存 | `git restore --staged 文件名` |
| 刚 commit 想撤回，但**保留**代码 | `git reset --soft HEAD~1` |
| 完全不要这次提交的改动 | `git reset --hard HEAD~1` |
| commit 信息写错了 | `git commit --amend -m "新的说明"` |
| 不知道该从哪查起 | `git reflog` |

其中 `git reflog` 是**终极后悔药**，它记录了你对仓库做过的几乎所有操作。哪怕是误删的分支、回退过头的提交，大多都能通过它找回来。

> ⚠️ **两点提醒**：
>
> 1. `git commit --amend` 和 `git reset` 都会**改写历史**，只建议用在**还没推送到远程**的提交上，否则会给协作者带来麻烦。
> 2. `git reset --hard` 会**直接丢弃**未保存的改动，执行前务必确认。

---

## 总结

好的 Git 习惯不是为了给别人看，而是为了保护未来的自己。

* **写清楚**：提交信息说明「做了什么」，方便回溯
* **小步走**：一个功能点一次提交，回退时才能精准
* **管好忽略**：`.gitignore` 挡掉依赖、密钥和产物
* **分支隔离**：`main` 稳、`develop` 动，新功能开特性分支
* **先拉后推**：避免冲突和推送失败
* **敢撤销**：`restore`、`reset`、`reflog` 是安全网

项目越大、时间越长，这些习惯的价值就越能体现出来。
